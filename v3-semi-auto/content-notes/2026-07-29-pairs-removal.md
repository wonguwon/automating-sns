# 하루 만에 걷어낸 중간 산출물 — pairs는 왜 필요 없어졌나 (2026-07-29)

카드뉴스 제작 페이지를 만들던 중, 바로 전날 설계했던 딥리서치의 핵심 산출물(pairs)을
사용자의 질문 하나로 하루 만에 제거하게 된 과정. "중간 산출물은 언제 만들 가치가 있나"라는
일반적인 파이프라인 설계 주제로 쓸 만하다.

## 원래 설계: 구조화된 (내용, 출처) 쌍

딥리서치 단계는 산출물을 두 개 만들었다 — 사람이 읽는 마크다운 조사 노트와, 다음 단계가
기계적으로 쓰는 `pairs.json`(사실 하나 + 그 사실이 나온 원문 URL의 쌍 배열). 의도는 그럴듯했다:

- 카드 슬라이드마다 출처 URL이 필수인데, 쌍 구조면 사실↔출처가 1:1로 매핑된다
- "이 배열에 있는 사실만 써라"로 환각을 통제하기 좋다
- 구조화된 입력이 프롬프트에서 다루기 깔끔해 보인다

## 사용자의 질문: "pairs 자체가 필요 없을 것 같은데?"

카드뉴스 생성까지 두 번 돌려본 시점에 사용자가 물었다 — "딥리서치를 한 이유는 참고자료를
만들기 위해서인데, 조사 노트를 주고 만들게 하면 되지 않나. pairs가 왜 필요하지?"

실데이터를 확인해보니 반박할 수가 없었다:

- **34개 쌍의 출처 URL이 전부 같은 주소였다.** 이 파이프라인은 후보 하나가 기사 1~3건에서
  나오므로, 출처는 "사실 단위"가 아니라 "소재 단위"로 수렴한다. 1:1 매핑이라는 핵심 가치가
  실제로는 아무 일도 하지 않고 있었다.
- 노트에 있던 배경·맥락·함의는 pairs로 쪼개는 과정에서 다 버려지고 있었다 — 마침 같은 날
  "스토리라인은 GPT가 유연하게 설계"하도록 바꾼 참이라, 재료를 스스로 빈곤하게 만드는 셈이었다.
- pairs를 만들기 위한 `---PAIRS---` 구분자 출력과 JSON 파싱 실패 처리 코드가 통째로
  유지비용이었다.

## 전환: 노트 전문 + 출처 URL 목록

pairs를 제거하고, 카드뉴스 생성 입력을 "조사 노트 전문 + 후보에 저장된 출처 URL 목록"으로
바꿨다. 슬라이드 출처 표시는 유지하되 "이 목록의 URL 중에서 골라라"로 충분했다.
바꾼 직후 생성 결과는 오히려 좋아졌다 — 노트에만 있던 사실(판매수량, 제조국 같은 디테일)이
카드에 올라오기 시작했다.

## 교훈

- **중간 산출물은 소비자가 그 구조를 실제로 쓸 때만 가치가 있다.** "매핑이 있으면 좋겠지"가
  아니라 "매핑이 실제 데이터에서 정보를 담는가"를 확인해야 한다. 우리 경우 매핑은 항상 같은
  값으로 퇴화해 있었다.
- **구조화는 공짜가 아니다.** 출력 형식 지시, 구분자 파싱, 실패 처리, 파일 하나가 전부
  유지비용이고, 쪼개는 과정에서 원래 자료의 맥락이 손실된다.
- **설계 검증은 스키마가 아니라 실데이터로 한다.** 이 결정을 가능하게 한 건 "34쌍 전부 같은
  URL"이라는 실제 파일 한 번 열어본 것이었다.
- 전날 만든 설계를 다음 날 걷어내는 것을 실패로 볼 필요는 없다 — 두 번 돌려봤기 때문에
  하루 만에 알 수 있었던 것이고, 늦게 발견할수록 걷어내는 비용만 커진다.
