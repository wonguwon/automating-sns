# AI 에이전트와 Streamlit 앱을 라이브로 같이 고칠 때 부딪힌 것들 (2026-07-28)

V3의 첫 실제 기능("컨텐츠 수집" 단계)을 Claude Code와 함께 만들면서, 사용자가 별도 터미널에서
`streamlit run app.py`를 직접 띄워놓고 동시에 만지고 있는 상태로 에이전트가 코드를 고치고
자기 테스트 서버도 따로 띄워 검증하는 식으로 작업이 진행됐다. 이 과정에서 나온 것들 중
일반적인 "AI와 페어 코딩" 콘텐츠로 쓸 만한 지점들.

## 1. 오래 떠 있는 프로세스는 파일을 고쳐도 모르는 척한다

`sources_store.py`에 함수(`update_feed`)를 하나 추가했는데, 사용자가 이미 켜놓고 있던
Streamlit 프로세스에서 `ImportError: cannot import name 'update_feed'`가 났다. 파일은 분명
고쳐져 있었는데도.

원인: Streamlit의 자동 rerun은 방금 저장한 페이지 스크립트는 다시 실행해주지만, 그 스크립트가
`import`하는 옆 모듈(`sources_store.py`)은 파이썬 프로세스가 처음 뜰 때 한 번 메모리에 캐싱된
채로 남아있다. 코드는 최신인데 실행 중인 프로세스의 "기억"은 옛날 버전인 상태 — 겉보기엔
"방금 고쳤는데 왜 안 돼?" 라는 흔한 당황 포인트다. 해결은 단순히 프로세스를 완전히
재시작(Ctrl+C 후 다시 실행)하는 것뿐, 코드 자체엔 문제가 없었다.

## 2. "이 드롭다운, 타이핑으로 막 바꿀 수 있으면 안 되는데"

리소스 그룹을 고르는 `st.selectbox`가 기본적으로 타이핑해서 옵션을 필터링하는 검색창처럼
동작한다. 사용자는 이게 "그냥 고르기만 하는 선택창"이었으면 했다. Streamlit 최신 버전엔
`filter_mode=None`(타이핑 필터링 자체를 끔)과 `accept_new_options=False`(목록에 없는 값은
애초에 선택값으로 확정 안 됨, 기본값)가 있어서 이걸로 해결했다 — 다만 실제로 테스트해보니
`filter_mode=None`이어도 열려있는 동안 키보드 입력 자체는 여전히 받아지고 일시적으로
"No results"를 보여주긴 했다. 중요한 건 Esc를 누르거나 포커스를 벗어나면 항상 유효한
옵션으로 되돌아온다는 것 — 문서에 적힌 설명과 실제 동작이 완전히 일치하진 않았지만, 데이터가
깨질 걱정은 없다는 확인은 직접 클릭해봐야 알 수 있었다.

## 3. 체크박스를 눌렀는데 "다른 엘리먼트가 클릭을 가로챈다"

Streamlit의 체크박스는 `<label>`이 실제 `<input>` 위를 감싸고 있는 구조라, Playwright 같은
자동화 도구가 좌표 기반으로 클릭하려 하면 "다른 엘리먼트가 pointer event를 가로챈다"며
타임아웃이 난다. 우회는 간단했다 — `element.click()`을 JS로 직접 실행(`browser_evaluate`)하면
DOM 레벨에서 클릭이 그대로 먹힌다. 사람이 마우스로 누르는 것과 자동화 도구가 "누르는 것"
사이에 이런 간극이 종종 있다는 사례.

## 4. 남의 세션을 안 죽이면서 내 테스트 서버만 정리하기

사용자가 8501(Streamlit 기본 포트)에서 자기 세션을 계속 띄워놓고 있는 동안, 에이전트는 검증을
위해 8765~8772번 포트로 테스트 서버를 여러 번 새로 띄우고 껐다. `tasklist`로 python.exe
프로세스를 나열하면 여러 개가 잡히는데, PID만 보고 무작정 죽이면 사용자의 작업 세션을
날려버릴 수 있다. `netstat -ano`로 각 PID가 실제로 어느 포트에 물려 있는지, 활성 연결
(ESTABLISHED)이 있는지까지 확인한 뒤 자기가 띄운 포트의 PID만 골라 종료하는 식으로 처리했다.
"실행 중인 프로세스를 정리해야 하는데 그게 누구 것인지 모른다"는 상황에서의 안전한 판단 방식.
