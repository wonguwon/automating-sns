# 커밋 분할 + pull/push

변경사항을 하나의 커밋으로 뭉치지 않고 의미 단위로 나눠 커밋한 뒤, `pull`·`push`까지 진행하는 스킬이다.
이 저장소(`ai-sns`)는 여러 버전(V1/V2/V3)과 도구 상태 파일이 섞여 있어, 커밋 대상을 자동으로 다 넣지
않고 매번 실제 diff를 보고 판단해야 한다.

## 언제 쓰는가

- 사용: 사용자가 "커밋해줘", "나눠서 커밋", "커밋하고 푸시해줘", "풀 푸쉬" 등으로 **명시적으로** 커밋/
  푸시를 요청했을 때.
- 안 씀: 커밋 요청 없이 코드만 수정하는 일반 작업 중에는 스스로 커밋을 실행하지 않는다. 작업 마무리
  시점에 "커밋할까요?" 하고 제안하는 것까지는 괜찮지만, 사용자가 확답하기 전에는 이 스킬의 실행 단계로
  넘어가지 않는다.
- API 키/환경변수 값은 어떤 경우에도 커밋 메시지나 보고에 그대로 노출하지 않는다.

## 절차

### 1. 현황 파악

- `git status`, `git diff`(staged + unstaged), `git log --oneline -10`을 실행해 실제 변경 내역과 기존
  커밋 메시지 스타일을 확인한다.
- 이 저장소는 `git rev-parse --show-toplevel`이 현재 작업 디렉터리(`v3-semi-auto`)보다 한 단계 위일 수
  있다 — repo root 기준으로 상태를 봐야 다른 버전 폴더(`versions/` 등)나 `.omc/` 같은 최상위 파일이
  누락되지 않는다.

### 2. 그룹화 제안

변경 파일을 의미 단위로 묶어 여러 커밋 그룹으로 나눈다. 그룹명은 매번 실제 diff 내용을 보고 정하며,
아래는 예시일 뿐 고정된 목록이 아니다.

- 예: 위키 문서 갱신, 특정 기능/단계 재설계, 콘텐츠 노트 추가 등.
- **제외 판단**: 프로젝트 소스로 보이지 않는 파일(도구/세션 캐시 — 예: `.omc/state/...`,
  `.playwright-mcp/` 같은 패턴)은 커밋 후보에서 제외한다. 왜 제외했는지, `.gitignore`에 추가하는 게
  나아 보이는지를 사용자에게 알린다. 특정 경로명을 미리 전제하지 말고 매번 실제 파일 성격을 보고
  판단한다.
- 그룹화 결과와 그룹별 파일 목록을 사용자에게 먼저 보여준다.

### 3. 커밋 메시지 초안

- 그룹별로 "무엇을/왜"에 집중한 커밋 메시지를 **한국어**로 작성한다(이 프로젝트의 위키·CLAUDE.md가 모두
  한국어이고, 기존 커밋은 "Initial commit" 하나뿐이라 정해진 다른 관례가 없다).
- 이 단계에서는 아직 `git add`/`git commit`을 실행하지 않는다.

### 4. 승인 대기

- 사용자가 그룹핑과 커밋 메시지를 승인(또는 수정 요청)하기 전에는 실제 커밋을 만들지 않는다.
- 수정 요청이 있으면 그룹/메시지를 다시 제시한다.

### 5. 커밋 실행

승인된 그룹만, 그룹 순서대로:

```
git add <해당 파일들>
git commit -m "$(cat <<'EOF'
<한 줄 요약>

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
```

- 전역 git 안전 수칙을 지킨다: `rebase -i` 금지, `--no-verify`/`--no-gpg-sign` 금지, 기존 커밋 amend
  금지, `git add -A`/`git add .` 같은 뭉뚱그린 스테이징 대신 그룹별 파일을 명시적으로 add한다.
- add 직후 `git status`로 실제 스테이징된 파일을 다시 확인해, 의도치 않은 파일(특히 비밀값이 들어있을
  수 있는 파일)이 섞이지 않았는지 점검한다.

### 6. pull

- 모든 그룹 커밋이 끝나면 `git pull --rebase origin <현재 브랜치>`로 원격 변경을 반영한다.
- 충돌이 나면 자동으로 해결하려 하지 말고 즉시 멈춰서 충돌 상태를 사용자에게 보고한다.

### 7. push

- 그룹·메시지 승인을 받은 시점에 이미 "커밋하고 푸시까지" 요청이 있었던 것이므로, pull이 충돌 없이
  끝나면 별도 재확인 없이 `git push`까지 진행한다.
- **force push는 어떤 경우에도 사용하지 않는다.** pull 충돌 등으로 정상 push가 안 되면 강제로 밀어붙이지
  말고 사용자에게 상황을 보고한다.

### 8. 최종 보고

CLAUDE.md의 "작업 종료 시 보고" 형식에 맞춰 다음을 정리한다.

- 생성된 커밋 목록(해시 + 메시지)
- pull/push 결과
- 커밋 대상에서 제외한 파일과 이유
- 확인하지 못한 사항

## 하지 않는 것

- 요청 범위를 벗어난 파일 정리(고아 파일 삭제 등)는 이 스킬의 역할이 아니다 — 그룹화·제외 제안까지만
  하고, 실제 삭제나 대규모 정리는 별도로 사용자 확인을 받는다.
- 실행/테스트하지 않은 변경을 "검증됨"이라고 커밋 메시지에 쓰지 않는다.
